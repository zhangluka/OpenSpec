# Review Code 增强说明

## 背景

原有 `/phsx:review-code` 命令聚焦于**规格合规性验证**——检查代码是否正确实现了 spec 中的需求、场景和约束。这在功能正确性维度已经做得不错，但缺少工程质量管理的深度。

参考 [sanyuan-skills/code-review-expert](https://github.com/sanyuan0704/sanyuan-skills/tree/main/skills/code-review-expert) 的设计，我们将安全扫描、架构审查、竞态条件检测和死代码识别能力融合进来，形成一个更完整的代码审查体系。

## 增强内容

### 1. Preflight 变更范围感知

**之前**：直接开始审查，不了解变更规模。

**现在**：
- 自动通过 `git diff --stat HEAD` 获取变更文件列表和行数
- 大 diff（500+ 行）主动警告用户建议分批审查
- 混合关注点（多模块变更）提示用户考虑拆分

**效果**：避免在大型变更中遗漏问题，提高审查的针对性。

### 2. 安全扫描（Layer 2.5）

新增 9 大类安全检查，每类都有具体的 grep 检查模式：

| 检查类型 | 检查内容 | 严重级别 |
|----------|----------|----------|
| XSS | `dangerouslySetInnerHTML`、未转义模板、innerHTML、`javascript:` 协议 | P0 |
| 注入 | SQL/NoSQL/命令注入（字符串拼接而非参数化查询） | P0 |
| SSRF | 用户可控 URL 未做 allowlist 校验 | P0 |
| 路径穿越 | 用户输入进入文件路径未消毒 | P0 |
| 认证/授权 | 缺失 auth guard、IDOR、信任客户端角色 | P0 |
| JWT | 算法混淆、弱密钥、缺失 exp 验证、payload 含敏感数据 | P0-P1 |
| 密钥泄露 | API key/token 出现在代码/配置/日志中 | P0 |
| 供应链 | 未锁定依赖、依赖混淆、CDN 无 SRI | P1 |
| 竞态条件 | TOCTOU、check-then-act、read-modify-write 无原子操作 | P0-P1 |

**效果**：在代码审查阶段就能捕获安全漏洞，而不是等到安全审计才发现。竞态条件检查特别有价值——这类 bug 在测试中很难复现，但在代码审查中可以通过模式识别发现。

### 3. 架构检查（Layer 2.5）

新增轻量级 SOLID 检查：

| 检查项 | 关注点 |
|--------|--------|
| 单一职责（SRP） | 函数是否承担过多职责（超过 3 个独立关注点）、"上帝函数"（超过 100 行） |
| 依赖方向 | 高层模块是否直接 `new` 低层实现、循环依赖、硬编码配置 |
| 副作用隔离 | 纯计算函数混入 I/O、隐藏的全局状态修改 |

**效果**：在实施阶段就发现架构问题，避免技术债务累积。

### 4. 死代码检测（Layer 3）

新增死代码识别：
- 未被引用的函数/变量
- 注释掉的代码块（应由版本控制保留历史）
- TODO/FIXME 标记的临时代码
- 永远不会执行的分支（`if false`、`return` 后的代码）

**效果**：保持代码库清洁，减少维护负担。

### 5. 严重级别对齐

将原有的 Critical/Important/Optional 三级体系对齐为 P0-P3 四级：

| 级别 | 含义 | 行动 |
|------|------|------|
| P0 | 安全漏洞、数据丢失、正确性 bug、spec 不合规 | 必须阻断合并 |
| P1 | 错误处理缺失、边界条件未覆盖、架构违规 | 合并前应修 |
| P2 | 可测试性、可观测性问题 | 修或创建 follow-up |
| P3 | 死代码、风格建议 | 可选改进 |

**效果**：更精细的优先级划分，团队可以更准确地分配修复资源。

### 6. 报告格式增强

审查报告新增以下章节：

- **Layer 2.5: Security Scan** — 漏洞类型 / 严重级别 / 状态 / 证据表格
- **Layer 2.5: Architecture Check** — 架构违规检查结果表格
- **Dead Code Candidates** — 死代码位置 / 类型 / 建议处理方式表格

**效果**：报告信息密度更高，读者可以快速定位安全和架构问题。

### 7. 下一步确认机制

审查完成后不再自动继续，而是提供明确的选项：
1. 修复所有 P0 和 P1 问题
2. 仅修复 P0 问题
3. 修复指定的问题
4. 不修复，仅记录

**效果**：将控制权交给用户，避免审查后的自动行为不符合预期。

## 未改变的部分

以下能力保持不变：
- 三层检查架构（Layer 1/2/3 的核心逻辑）
- 场景覆盖率验证（WHEN/THEN 对照）
- 项目配置扫描（ESLint/Prettier/tsconfig）
- 评分标准（1-5 分制）
- 报告保存机制（`phspec/changes/<name>/reviews/`）

## 对比 sanyuan code-review-expert

| 维度 | sanyuan | OpenSpec（增强后） |
|------|---------|-------------------|
| 安全检查 | 完整（9 大类） | 完整（9 大类，全量嵌入） |
| SOLID 检查 | 完整（5 原则） | 轻量（SRP + 依赖方向 + 副作用） |
| 竞态条件 | 深入（含代码示例） | 深入（含关键提问清单） |
| 死代码检测 | 完整（含删除计划） | 基础（识别 + 建议） |
| Spec 合规性 | 无 | 核心能力（WHEN/THEN 覆盖） |
| 场景覆盖验证 | 无 | 核心能力（逐 Scenario 验证） |
| 项目配置感知 | 无 | 有（ESLint/Prettier/tsconfig） |
| 工作流集成 | 独立工具 | 深度集成（phspec status、增量规范） |

OpenSpec 增强后的优势在于：安全检查与 spec 合规性验证的结合。例如，一个 P0 安全漏洞不仅会被标记为安全问题，还会关联到它违反了 spec 中的哪条 Requirement。
