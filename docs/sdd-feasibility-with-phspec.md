# 通过 PhSpec 落地 SDD 的可行性分析

本文结合 [zhangluka/SDD](https://github.com/zhangluka/SDD) 的规范驱动开发（Specification-Driven Development）理念与 PhSpec 的能力，分析在实际项目中用 PhSpec 落地 SDD 的可行性。

---

## 一、SDD 核心要求摘要（来自 zhangluka/SDD）

| 维度                 | SDD 要求                                                                                                                        |
| -------------------- | ------------------------------------------------------------------------------------------------------------------------------- |
| **定位**             | 规范 = 全流程唯一真相源；契约先行；可执行、可验证、机器可读                                                                     |
| **六阶段**           | Specify（规格定义）→ Plan（方案规划）→ Tasks（任务拆解）→ Implement（实现与验证）→ Deliver（交付与集成）→ Iterate（迭代与运维） |
| **规范形态**         | 按功能/模块的规格文件（Markdown 或 YAML/JSON），与代码同库；含功能 ID、范围、输入输出、成功/失败/边界/异常、**可验收条目**      |
| **验收标准**         | 「给定 X，系统应 Y，可观测/可验证为 Z」；可与测试用例一一对应                                                                   |
| **与「怎么做」分离** | 规格只写做什么/验什么；技术选型、实现细节放在 Plan 阶段                                                                         |
| **多团队**           | 每需求唯一规格 ID；跨团队接口在规格中以契约形式写清                                                                             |
| **工具**             | 规范即文件、与任务/PR 绑定、AI 消费规格片段、轻量 CLI（校验、追溯）                                                             |

---

## 二、PhSpec 能力与 SDD 阶段对照

### 2.1 阶段映射

| SDD 阶段                 | PhSpec 对应                                               | 说明                                                                                                                 |
| ------------------------ | --------------------------------------------------------- | -------------------------------------------------------------------------------------------------------------------- |
| **Specify 规格定义**     | 变更内 `proposal.md` + `specs/<领域>/spec.md`（增量规范） | 提案写动机、范围、能力；增量规范写 ADDED/MODIFIED/REMOVED 的需求与场景（Given/When/Then），只定义「做什么/验收标准」 |
| **Plan 方案规划**        | 变更内 `design.md`                                        | 技术方案、决策、风险；与规格分离，设计引用「实现的能力」                                                             |
| **Tasks 任务拆解**       | 变更内 `tasks.md`                                         | 可勾选任务列表，可并行、可验证；AI 与开发者按此执行                                                                  |
| **Implement 实现与验证** | `/phsx:apply` + `phspec validate` + `/phsx:verify`        | 按 tasks 推进，校验制品结构与实现一致性                                                                              |
| **Deliver 交付与集成**   | `/phsx:archive`                                           | 增量合并回 `phspec/specs/` 主规范，变更移入 archive，主规范成为当前「法定」行为                                      |
| **Iterate 迭代与运维**   | 新需求 = 新 change；先改规范再开发                        | 任何变更都先进入 `phspec/changes/<name>/`，评审后再 apply，归档后主规范与代码库一致                                  |

结论：**SDD 的六阶段在 PhSpec 中均有直接对应**，且顺序与 SDD 一致（先提案/规范，再设计/任务，再实现，最后归档）。

### 2.2 规范形态与「唯一真相源」

| SDD 要求              | PhSpec 支持情况                                                                                                              |
| --------------------- | ---------------------------------------------------------------------------------------------------------------------------- |
| 规范与代码同库        | ✅ `phspec/specs/`、`phspec/changes/` 与代码同仓库、同版本管理                                                               |
| 按功能/模块的规格文件 | ✅ 按领域子目录（如 `auth/`、`payments/`）每个一个 `spec.md`                                                                 |
| 结构化、可解析        | ✅ 固定 Markdown 结构（Purpose、Requirements、Requirement、Scenario）；解析为 `Spec`（name, overview, requirements[]）并校验 |
| 机器可读 / 可导出     | ✅ `phspec show <spec-id> --json`、`phspec validate --specs --json` 等输出结构化数据，便于脚本与 AI 消费                     |
| 单一事实来源          | ✅ 主规范在 `phspec/specs/`；仅通过「变更 → 实施 → 归档」更新，禁止直接手改主规范与变更无关内容                              |

### 2.3 验收标准与可验证性

| SDD 要求                                 | PhSpec 支持情况                                                                                                                                                                 |
| ---------------------------------------- | ------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| 验收写成「给定 X，系统应 Y，可验证为 Z」 | ✅ 规范格式要求 `#### Scenario:` 与 GIVEN/WHEN/THEN 风格；rules 可约定「每条需求至少一个场景」                                                                                  |
| 验收可检验                               | ⚠️ **部分支持**：PhSpec 校验**规范结构**（Requirement 含 SHALL/MUST、至少一场景等），**不自动生成测试或做运行时断言**。可检验性依赖团队把场景转化为测试用例（人工或自建脚本）。 |
| 规范与测试用例对应                       | 流程支持：可在 tasks 中写「为 AC-x 补充测试」；无内置从 spec 生成测试骨架的工具                                                                                                 |

### 2.4 契约先行与角色协同

| SDD 要求                 | PhSpec 支持情况                                                                                                        |
| ------------------------ | ---------------------------------------------------------------------------------------------------------------------- |
| 先完整定义再做设计与编码 | ✅ 工作流强制：先 `proposal` + `specs`（+ 可选 `design`、`tasks`），再 `/phsx:apply`                                   |
| 全角色参与规范           | ✅ 通过 `phspec/config.yaml` 的 `context` 与 `rules` 统一约定；评审以「提案 + 增量规范」为材料，BA/开发/测试可共同维护 |
| 规格与「怎么做」分离     | ✅ 规格只写需求与场景；`design.md` 写技术方案并引用能力名，不混入 spec                                                 |

### 2.5 多团队与规格 ID

| SDD 要求          | PhSpec 支持情况                                                                                                                   |
| ----------------- | --------------------------------------------------------------------------------------------------------------------------------- |
| 每需求唯一规格 ID | ✅ 用「变更名」+「能力（领域）名」即可：如 `add-export-csv` 变更下的 `api/`、`ui/`；跨团队时同一变更下多份 `specs/<领域>/spec.md` |
| 跨团队接口契约    | ✅ 在对应领域的 `spec.md` 中写清输入输出、错误码、约束；设计阶段再细化为协议                                                      |
| 共享与可见性      | ✅ `phspec/` 随代码库共享；变更与归档均有目录与历史可追溯                                                                         |

### 2.6 工具与自动化

| SDD 建议             | PhSpec 支持情况                                                                                                |
| -------------------- | -------------------------------------------------------------------------------------------------------------- |
| 规范即文件、即数据   | ✅ 规范为 Markdown 文件，解析后为结构化数据，可被脚本读取                                                      |
| 规范与任务/代码绑定  | ✅ 变更目录内 proposal/specs/design/tasks 与实现一一对应；MR/PR 层面可约定「关联 change 名」并在 CR 中检查     |
| AI 使用规格片段      | ✅ 技能与指令会把当前变更的 proposal、specs、design、tasks 作为上下文提供给 AI；可强调「以规格与验收条件为准」 |
| 轻量 CLI：校验、追溯 | ✅ `phspec validate`（变更/规范）、`phspec list`、`phspec show`、`phspec status` 等，满足校验与追溯            |

## 三、可行性结论

### 3.1 总体结论

**通过 PhSpec 在实际项目中落地 SDD 是可行的**，且与 zhangluka/SDD 文档中的「不推倒重来、先立规范这一源、规范从现有产出物里长出来」思路一致。PhSpec 已覆盖：

- 六阶段闭环（Specify → Plan → Tasks → Implement → Deliver → Iterate）
- 规范即唯一真相源、与代码同库、结构化与机器可读
- 契约先行、规格与设计分离、多能力/多团队在同一变更下组织
- 轻量 CLI 与多 AI 工具集成，便于「先改规范再改代码」的纪律

### 3.2 强匹配点

1. **流程对齐**：SDD 的「先规格再设计再实现再归档」与 PhSpec 的 `/phsx:new` → `/phsx:ff` → `/phsx:apply` → `/phsx:archive` 一致。
2. **棕地友好**：SDD 强调在多团队 + 传统模式下插入「结构化规格」而不废除现有 Word/会议；PhSpec 的棕地最佳实践（先为被改模块建主规范、再开变更）与之完全契合。
3. **验收表达**：Given/When/Then 与 SDD 的「给定 X，系统应 Y，可验证为 Z」同构，便于在评审与 CR 中统一语言。
4. **可配置规则**：`config.yaml` 的 `rules.specs` 可强制「每条需求至少一个场景」「先查阅主规范再写增量」，与 SDD 的评审与书写约定一致。

### 3.3 需要补齐或约定的部分

| 项目                  | 说明                                       | 建议                                                                                                        |
| --------------------- | ------------------------------------------ | ----------------------------------------------------------------------------------------------------------- |
| **验收的自动可检验**  | PhSpec 不自动从规范生成测试或做运行时断言  | 团队约定：每个 Scenario 对应一条测试或验收清单；或自建脚本从 `phspec show --json` 生成测试骨架/清单         |
| **规格 ID 命名**      | SDD 常提 SPEC-2025-xxx 这类 ID             | 用「变更名 + 能力名」即可（如 `add-export-csv` + `api`）；若需显式 ID，可在 proposal 或 spec 标题中约定     |
| **与 Word/BA 的衔接** | 规范从 Word 需求「长出来」需人工或额外工具 | 流程上：需求澄清会出口为「结构化规格」；由 BA 主导在 PhSpec 变更中起草 proposal + specs，不改变 PhSpec 本体 |
| **MR/PR 与规格绑定**  | SDD 建议 MR 关联规格 ID、门禁检查          | 在 CR 清单与 CI 中约定：改动需关联 change 名、或检查 `phspec/` 是否有对应变更/主规范更新                    |

## 四、落地建议（与 zhangluka/SDD 分阶段推进一致）

1. **试点**：选一个需求边界清晰的项目，在「需求澄清」之后增加「PhSpec 变更 + 规格评审」；用 `phspec/config.yaml` 注入技术栈与书写规则，要求设计/任务写明实现的能力名。
2. **绑定**：设计评审时检查「是否覆盖规格中的全部验收条件」；MR 描述或任务单中填写变更名（如 `add-export-csv`）。
3. **交付依据**：用户验收与结项以「主规范 + 归档后的变更」为验收清单，而非仅 Word 或口头约定。
4. **迭代纪律**：需求/bug/重构均先新建或更新 PhSpec 变更并评审，再 `/phsx:apply`，养成「改代码必先改规范」的习惯。
5. **可选增强**：在 2～3 个团队稳定用 PhSpec 后，再考虑从 `phspec show --json` 生成验收清单或测试模板、或在 CI 中做简单门禁（如变更目录存在性、validate 通过）。

## 五、总结

| 维度         | 结论                                                                                         |
| ------------ | -------------------------------------------------------------------------------------------- |
| **流程覆盖** | PhSpec 完整覆盖 SDD 六阶段，且顺序与理念一致                                                 |
| **规范形态** | 单一真相源、结构化、机器可读、契约先行均支持                                                 |
| **验收标准** | 格式与表达支持；自动可检验需团队约定或自建工具                                               |
| **多团队**   | 单变更多领域、主规范共享、接口写在 spec 中，可行                                             |
| **落地方式** | 与 SDD 文档「不推倒重来、先立规范、分阶段推进」完全兼容，可直接以 PhSpec 作为 SDD 的落地工具 |

因此，**在实际项目中通过 PhSpec 落地 SDD 是可行的**；在补齐「验收可检验」与「与现有 BA/Word/门禁」的流程约定后，即可在试点基础上推广。
