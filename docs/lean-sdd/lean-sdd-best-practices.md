# Lean-SDD 最佳实践指南

Lean-SDD 是 OpenSpec 的精益规格驱动开发工作流，将传统软件开发的核心文档精简为四个制品，并针对 AI 辅助开发进行了优化。本指南基于 [SDD（Specification-Driven Development）](https://github.com/zhangluka/SDD) 的核心理念设计。

---

## 核心设计理念

Lean-SDD 遵循 SDD 的七条核心原则：

1. **规范 = 全流程唯一真相源**：业务需求、技术实现、测试验收、运维迭代均以规范为法定依据，消除多源信息割裂。
2. **契约先行**：先完整定义「做什么 / 不做什么、成功 / 失败标准、边界与异常、验收标准」，全角色评审通过后再进入设计与编码。
3. **规范可执行、可验证、机器可读**：结构化、可被 AI 和工具解析、可自动化校验，避免模糊描述。
4. **全角色协同共识**：规范的定义与评审覆盖产品、开发、测试、运维等角色，各角色从自身视角补充边界与验收标准。
5. **风险左移**：在规格阶段解决歧义与缺陷，降低编码与上线后的返工成本。
6. **规范是核心资产，代码是衍生物**：可复用、可迭代的是规范体系；规范稳定则可随技术栈 / 人员 / AI 工具再生实现。
7. **全生命周期闭环**：任何修改都先更新规范、评审，再改代码 / 测试 / 文档，保证规范与实现永远同步。

## 工作流总览

```text
requirement.md ──► specs/**/*.md ──► plan.md ──► tasks.md ──► apply（实施）
  需求澄清说明书      详细规范       详细设计说明书  任务拆解      代码实现
```

**制品依赖关系：**

```text
requirement ──► specs    （需求 → 规范）
            ──► plan     （需求 → 详细设计）
                    specs ──┐
                    plan  ──┴──► tasks（规范 + 设计 → 任务）
                                       tasks ──► apply（任务 → 实施）
```

**与传统开发流程的对标：**

| Lean-SDD 制品  | 传统文档角色   | 核心职责                           |
| -------------- | -------------- | ---------------------------------- |
| requirement.md | 需求澄清说明书 | 做什么 / 为什么 / 验收标准         |
| specs/         | 详细功能规范   | 场景化的 WHEN/THEN 规范            |
| plan.md        | 详细设计说明书 | 怎么做 / 模块划分 / 影响范围分析   |
| tasks.md       | 任务工单       | 最小任务单元 / 红绿测试 / 并行标注 |

## 阶段一：需求澄清（requirement.md）

### 输入

接受多种形式的需求输入：

- 一段自然语言描述（口头沟通、聊天记录、邮件等）
- Markdown 格式的需求文档
- Word 格式的需求说明书

### 输出原则

将模糊需求转化为**无歧义、可验证**的功能规格：

- **只定义「做什么」和「为什么」**，不涉及「怎么做」
- 每条功能需求**必须**附带 WHEN/THEN 验收标准
- 发现歧义或矛盾时，在「待澄清项」中明确列出，不做假设

### 最佳实践

1. **消灭模糊词**：遇到「大概」「尽量」「适当」「合理」等词，必须转化为具体指标。例如「响应要快」→「接口响应时间 SHALL 不超过 200ms（P99）」。

2. **剥离实现细节**：如果原始需求中出现「用 Redis 缓存」「用 React 实现」等技术选型，将其剥离到备注，不混入需求正文。实现方案属于 plan.md 的职责。

3. **一条需求一个验收标准**：避免将多个行为混在同一条需求中。如果一条需求需要多个 WHEN/THEN，考虑拆分。

4. **明确边界**：「不做什么」和「做什么」同样重要。明确排除的内容能避免后续的范围蔓延。

### 质量自检清单

- [ ] 每条功能需求都有对应的验收标准？
- [ ] 不存在模糊词（大概、尽量、适当、合理）？
- [ ] 没有混入实现细节？
- [ ] 边界与排除已明确？
- [ ] 待澄清项已列出且无遗漏？

## 阶段二：详细规范（specs/）

### 定位

将 requirement.md 中的功能需求展开为场景化的详细规范，使用 WHEN/THEN 格式定义每个行为的具体场景。

### 最佳实践

1. **一个能力一个规范文件**：按 requirement.md 中的功能需求分组，每个能力对应 `specs/<capability>/spec.md`。

2. **场景覆盖要完整**：正常路径、边界情况、异常路径都需要对应的场景。

3. **使用强制性语言**：需求描述使用 SHALL/MUST（强制），避免 should/may（建议）。

4. **场景即测试用例**：每个 `#### Scenario` 都应该可以直接转化为一个自动化测试。

---

## 阶段三：详细设计说明书（plan.md）

### 定位

开发者撰写，面向 BA、测试、其他开发阐述「我打算怎么实现这些需求」。聚焦业务模块划分与职责、模块间协作关系、影响范围分析。粒度到业务模块/目录级别，不深入代码实现细节。

### 最佳实践

1. **面向多角色可读**：用通俗易懂的语言撰写，确保非开发角色（BA、测试）也能理解设计意图。避免大段代码或技术术语堆砌。

2. **模块划分清晰**：按业务模块分节，每个模块说明职责、改动内容、与其他模块的协作关系、所在目录。

3. **影响范围必须分析**：明确本次变更对现有功能/模块的影响，标注需要回归测试的区域。这是测试团队最关注的部分。

4. **不重复业务描述**：plan.md 聚焦「怎么做」，不重复 requirement.md 中已有的「做什么」和「为什么」。需要引用时指向 requirement.md 中的条目编号。

5. **遵循项目既有规范**：不做技术选型说明，跟随项目整体已有的技术栈和框架约定即可。不使用 MUST/SHALL 等规范性表述，那是 specs 的职责。

---

## 阶段四：任务拆解（tasks.md）

### 定位

将 plan.md 的详细设计拆解为可执行、可验证、可并行的最小任务单元，为 AI 和开发者提供明确的执行路径。

### 最佳实践

1. **最小任务单元**：每个任务应是单一职责、可独立完成的最小工作单元。如果一个任务描述中出现「和」「以及」，考虑拆分。

2. **红绿测试不可省略**：每个任务必须包含至少一个 🟢 成功案例和一个 🔴 失败案例。这是验收的唯一依据。

   ```
   - 🟢 WHEN 有效输入 → THEN 返回预期结果
   - 🔴 WHEN 无效输入 → THEN 抛出明确错误
   ```

3. **伪代码降低歧义**：对复杂逻辑，提供伪代码级别的描述。对简单任务（如配置修改）可省略。

4. **标注依赖关系**：明确每个任务的前置依赖，无依赖的任务可并行执行。这让 AI 能更高效地规划执行顺序。

5. **任务粒度对齐**：一个任务应在一次 AI 会话中完成。如果预估需要多次对话，拆得更细。

## 阶段五：代码实施（apply）

### 实施三原则

**原则一：遵守项目规范与编码规范**

- 遵循项目已有的代码风格、命名约定、目录结构
- 遵守 `config.yaml` 中 context 声明的技术栈约束
- 新增代码与既有代码库保持一致

**原则二：以规格为准绳校验实现**

- 每完成一个任务，对照 requirement.md 中对应的功能需求与验收标准自检
- 执行 tasks.md 中的红绿测试：🟢 成功案例通过、🔴 失败案例按预期处理
- 实现不得偏离 plan.md 中的模块设计与协作关系

**原则三：以规格为唯一依据完成验收**

- 任务完成的判定标准：requirement.md 中的验收标准全部满足
- tasks.md 中的红绿测试全部通过
- 不引入规格之外的额外功能（避免范围蔓延）

### 最佳实践

1. **实现→自检→勾选**：每完成一条任务，先对照规格自检，确认通过后再勾选 `- [x]`。

2. **发现问题先暂停**：如果实现过程中发现规格有歧义或缺失，暂停并提出澄清，不要自行假设。

3. **按依赖顺序执行**：参照 tasks.md 中的依赖标注，先完成无依赖的任务，再完成有前置依赖的任务。

4. **范围蔓延零容忍**：只实现规格中定义的功能。发现「顺手加个功能」的冲动时，记录到后续变更中。

---

## 阶段六：交付与验收

### 定位

对应 SDD 的 Deliver 阶段——以规格为唯一依据完成验收、集成、上线，确保交付物符合业务规格。

### 验收流程

1. **逐条对照验收标准**：以 requirement.md 中的功能需求及验收标准为验收清单，逐条确认。
2. **红绿测试全量通过**：tasks.md 中的 🟢 成功案例和 🔴 失败案例全部通过，作为验收的硬性门槛。
3. **规格覆盖度检查**：确认所有 requirement.md 中的功能需求在代码中都有对应实现，无遗漏。

### 最佳实践

1. **验收标准格式化**：每条验收写成「给定 X，系统应 Y，可验证方式 Z」，确保可观测、可断言。

2. **不接受规格外功能**：交付物只包含规格中定义的功能。额外功能即使已实现，也应在验收时记录为后续变更，不计入本次交付。

3. **验收结果可追溯**：验收结果应记录在案，与规格 ID 关联，便于后续审计和回溯。

---

## 阶段七：迭代与变更

### 定位

对应 SDD 的 Iterate 阶段——任何变更、修 bug、重构都先更新规格并评审，再基于新规格执行开发，实现「规格领先于代码，代码对齐规格」。

### 变更纪律

**先改规范，再改代码。** 这是 SDD 全生命周期闭环的核心纪律。

1. **需求变更**：先更新 requirement.md → 评审通过 → 更新 plan.md 和 tasks.md → 实施
2. **Bug 修复**：先确认是否为规格缺失 → 若是，补充规格 → 再修代码
3. **重构**：确认重构不影响规格中的验收标准 → 若影响，先更新规格 → 再重构

### 最佳实践

1. **变更必关联规格**：每次代码变更（PR/MR）应关联对应的规格条目。无规格关联的变更需要额外审查。

2. **规格版本化**：规格随代码同库、同版本管理。通过 Git 历史可追溯任何规格的变更过程。

3. **规格评审前置**：规格变更需评审通过后才能进入开发。评审确认变更对既有功能的影响范围。

## 全角色协同

Lean-SDD 虽然为 AI 辅助开发优化，但在团队场景下同样适用。规范的定义与评审应覆盖多角色。

### 各角色职责

| 角色        | 在 Lean-SDD 中的职责                                                   |
| ----------- | ---------------------------------------------------------------------- |
| 产品 / BA   | 主导 requirement.md 的起草；提供业务目标、边界和验收标准               |
| 开发 / 架构 | 主导 plan.md 的编写；参与 requirement.md 评审，补充技术可行性分析      |
| 测试 / QA   | 参与 requirement.md 评审，补充异常路径和边界场景；以红绿测试为验收依据 |
| 运维 / SRE  | 参与 plan.md 评审，补充部署、监控、安全等影响范围                      |
| AI 助手     | 在规格指导下执行 tasks.md 中的任务，以规格为准绳自检                   |

### 协同要点

1. **规格评审覆盖多角色**：requirement.md 评审至少包括产品 + 开发 + 测试；plan.md 评审至少包括开发 + 测试。

2. **评审通过 = 规格冻结**：评审通过后的规格作为本迭代的法定依据。后续变更走变更流程。

3. **一个需求一个规格 ID**：跨团队时，各团队引用同一份规格。在 requirement.md 中按模块拆分验收标准，明确各团队的交付边界。

## 落地成功标准

如何判断 Lean-SDD 用对了？从以下维度观察：

| 维度            | 观察指标                                                      |
| --------------- | ------------------------------------------------------------- |
| **规范覆盖**    | 核心功能是否都有对应的 requirement.md，是否有评审记录         |
| **变更纪律**    | 需求变更 / bug / 重构是否先改规格再开发（可通过 PR 抽样检查） |
| **可追溯性**    | 从规格能追溯到任务与代码，从代码能追溯到规格                  |
| **质量与返工**  | 同类需求在采用 Lean-SDD 前后，返工率、线上缺陷是否下降        |
| **AI 使用效果** | 以规范为输入的 AI 生成任务，一次通过率是否提升                |
| **团队共识**    | 各角色是否认可规格内容，是否减少了「需求理解不一致」的问题    |

## 与现有交付物的关系

| 现有交付物      | 与 Lean-SDD 的关系                                                 |
| --------------- | ------------------------------------------------------------------ |
| Word 需求说明书 | 保留为输入源，但法定依据逐步转为 requirement.md                    |
| 会议与需求澄清  | 保留，但澄清的输出从「会议纪要」升级为「更新后的 requirement.md」  |
| 总体 / 详细设计 | 由 plan.md 承担，阐述模块划分与实现方案                            |
| 测试用例        | 与 tasks.md 中的红绿测试对齐；specs/ 中的场景可直接转化为测试      |
| 验收与结项      | 以 requirement.md 的验收标准为验收清单，不再以 Word 或口头约定为准 |

## 常见反模式

| 反模式               | 问题                            | 正确做法                                            |
| -------------------- | ------------------------------- | --------------------------------------------------- |
| 需求中混入实现       | requirement.md 写了「用 Redis」 | 需求只写「缓存 SHALL 支持 TTL」，实现方案放 plan.md |
| 模糊验收标准         | 「系统应该快速响应」            | 「接口 P99 响应时间 SHALL ≤ 200ms」                 |
| 任务缺少红绿测试     | 无法判定任务是否完成            | 每个任务至少 1 个 🟢 + 1 个 🔴                      |
| 跳过 plan 直接写代码 | 缺少设计共识，实现方向不可控    | 先完成 plan.md 再拆解任务                           |
| 实现偏离规格不暂停   | 交付物与需求不一致              | 发现偏差立即暂停澄清                                |
| 一个任务包含多个职责 | 无法独立验证、无法并行          | 拆分为单一职责的最小单元                            |

## 快速开始

```bash
# 1. 初始化项目（自动使用 lean-sdd）
phspec init --tools cursor

# 2. 创建新变更
phspec new change add-user-export

# 3. 逐步创建制品
# /opsx:continue  -- 逐个创建
# /opsx:ff         -- 一次性创建全部

# 4. 实施任务
# /opsx:apply

# 5. 归档
# /opsx:archive
```
